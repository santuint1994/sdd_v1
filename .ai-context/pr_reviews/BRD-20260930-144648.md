- **Review Comments:**

### 1. Authentication & Session Management
The system shall implement the following authentication rules:
- Each user shall have an individual login account.
- Passwords shall be stored only as secure hashes.
- Plaintext passwords shall never be stored in the database, application logs or audit logs.
- Temporary passwords shall expire after first successful login or as defined by the security policy.
- Users must change their temporary password during first login.
- The system shall prevent login after the account is deactivated or locked.
- Failed login attempts shall be controlled through an agreed account-locking mechanism.
- Session timeout and idle timeout shall be implemented as per the approved security configuration.
- Password reset shall invalidate existing sessions where applicable.
- A user whose account is deactivated shall no longer be able to access protected APIs or active sessions.
- MFA/SSO shall remain out of scope unless separately approved.

Configuration values such as maximum failed attempts, lock duration, session timeout
and password complexity shall be confirmed before development completion.

### 2. Role & API-Level Authorization
Role-based and organisation-scope authorization shall be enforced at both:
- Frontend/UI level
- Backend/API level

Hiding a menu or button in the UI shall not be considered sufficient security.

For every API request, the system shall validate:
`User → Role → Organisation Scope → Requested Resource → Requested Action`

Users must not be able to access or modify employees, requests, documents, vacancies
or tasks outside their authorised scope by directly calling an API.

Unauthorized access attempts shall be rejected without exposing restricted employee
or organisational information.

### 3. Workflow State Management
The transfer workflow shall use a controlled state-transition model. Only valid status
transitions shall be permitted.

The system shall define and enforce:
- Current status
- Allowed next status
- User/role allowed to perform the transition
- Required action/reason
- Notification trigger
- Whether the request remains editable
- Whether vacancy capacity is affected
- Whether downstream tasks can be created

The following scenarios shall be supported: Submit, Approve, Reject, Request
clarification, Respond to clarification, Withdraw, Block, Resume, Reassign, HR metadata
change, Receiving Manager re-approval, IT Final Approval, Complete.

Invalid status transitions shall be rejected by the backend.

### 4. Vacancy Reservation & Capacity
Vacancy capacity shall be managed transactionally. The system shall follow:
`Available Capacity = Capacity − Allocated/Reserved`

The system shall:
- Reserve capacity only after HR validation/approval.
- Prevent allocation beyond available capacity.
- Prevent two concurrent HR users from consuming the same final available position.
- Use database transaction/concurrency control for reservation.
- Release reservation when the associated transfer no longer requires it.
- Define the behaviour when a transfer is rejected, withdrawn, cancelled, blocked or completed.
- Define the behaviour when HR changes the selected vacancy after reservation.
- Prevent new allocation against Full, On Hold or Closed vacancies.

Existing in-progress requests shall follow the defined in-flight request rules if
vacancy status changes.

### 5. Employee Eligibility
The system shall validate employee eligibility before allowing a transfer to proceed.
The business shall provide the applicable eligibility rules, including:
- Employment status
- Minimum tenure, if applicable
- Existing transfer restrictions
- Pending transfer restrictions
- Other applicable HR eligibility conditions

The system shall not allow developers to assume eligibility rules that have not been
approved.

### 6. Multiple Active Transfer Requests
The BRD shall define whether an employee can have multiple active transfer requests.
The following behaviour must be confirmed:
- Whether only one active transfer is allowed per employee.
- Whether multiple requests can be submitted.
- Whether the same vacancy can be requested more than once.
- Whether a withdrawn/rejected request allows a new request.
- Whether a new request requires closure of an existing request.

The selected rule shall be enforced at application/database level.

### 7. Employee Data Source of Truth
For employee and organisation information, the authoritative source shall be defined
for each field. The following fields shall have a clearly identified source of truth:
Employee ID, Employee Name, Email, Department/Business Unit, Designation, Location,
Reporting Manager, Employment Status, HR assignment, other organisation metadata.

Where portal data differs from the authoritative source, the system shall follow the
agreed source-of-truth rule.

### 8. Effective Transfer Date
The system shall validate the Effective Transfer Date according to approved business
rules. The BRD shall define:
- Whether past dates are allowed.
- Whether the current date is allowed.
- Whether future dates are mandatory.
- Minimum notice period, if applicable.
- Who can modify the date.
- Whether modification requires re-approval.
- Behaviour when approval occurs after the requested effective date.
- Whether weekends/holidays are allowed.

### 9. HR Organisation Metadata Changes
When HR changes a previously approved Department/Business Unit, Designation, Location
or Reporting Manager, the system shall apply the defined re-approval rule.

When Receiving Manager approval is enabled:
`HR Change → Receiving Manager Re-approval → HR Confirmation → Payroll/IT Activities → IT Final Approval → Completed`

The audit log shall capture: previous value, new value, changed by, date/time, reason,
re-approval triggered, Receiving Manager decision, decision date/time, decision
remarks.

This requirement is already established in the current BRD (BRD-024) and should remain
mandatory.

### 10. Payroll Task Completion
The system shall clearly identify when a required Payroll activity is completed. The
completion status shall be based on the approved source:
- Manual completion by authorised user, or
- Payroll system/API response, or
- Approved callback/status update.

IT Final Approval shall not be permitted while a mandatory Payroll activity remains
incomplete.

Payroll calculation, compensation and statutory processing shall remain outside the
portal. The portal shall only coordinate the Payroll activity and its status.

### 11. IT Final Approval
IT Final Approval shall remain the final completion gate.
- When IT work is required: `IT Task Completion → IT Final Approval → Transfer Completed`
- When IT work is not required: `No IT Action Required → IT Final Approval → Transfer Completed`

The transfer shall never become Completed based only on Reporting Manager approval,
Receiving Manager approval, HR approval, or Payroll completion.

IT Final Approval is mandatory for every transfer as defined in the current BRD.

### 12. Integration Requirements
For each external integration, the integration contract shall be available before
implementation. The integration definition shall include: API/interface,
authentication, request format, response format, required fields, success response,
business failure response, technical failure response, timeout, retry behaviour,
duplicate request handling, idempotency mechanism, status mapping, error handling,
source of truth.

The portal shall not create duplicate downstream transactions when an integration
request is retried. Integration failures shall be visible, auditable and recoverable.

This aligns with the existing NFR requirement for recoverable integration failures and
protection against duplicate downstream execution (NFR-006).

### 13. Document Upload & Access
The system shall enforce document security at API/server level. The following shall be
defined: allowed file formats, maximum file size, MIME type validation, file extension
validation, file-name sanitisation, secure storage location, download/access mechanism,
role and organisation-scope validation, unauthorized download prevention.

Documents shall not be directly accessible through an unrestricted public URL. Every
document access shall validate whether the requesting user has permission to access
the associated employee/transfer.

Current BRD already defines PDF/image-only documents and role/organisation-based access
(BRD-021).

### 14. Transfer Request Editing
The system shall define whether the employee can edit a submitted transfer request.
The BRD shall specify:
- Which fields can be edited.
- Until which workflow stage editing is allowed.
- Whether approved fields can be modified.
- Whether changes trigger re-approval.
- Whether the original values remain available in audit history.

No approved information should be silently overwritten.

### 15. Withdrawal
The employee may withdraw a transfer request only during the permitted workflow
stages. The system shall define:
- Last stage where withdrawal is allowed.
- Whether reason is mandatory.
- What happens to vacancy reservation.
- What happens to Payroll/IT tasks.
- Whether downstream tasks are cancelled.
- Whether the request can be reopened.

Withdrawal shall be audited.

### 16. Rejection & Resubmission
When a transfer is rejected:
- Rejection reason shall be mandatory.
- Rejection shall be recorded in workflow history.
- The employee shall be notified.
- The request shall move to the defined final/rejected state.

If resubmission is allowed, the BRD shall define:
- Who can resubmit.
- Whether a new transfer reference is generated.
- Whether previous approvals remain valid.
- Whether vacancy availability is checked again.
- Whether the complete workflow starts again.

### 17. Clarification
When a reviewer requests clarification:
- Clarification reason/question shall be recorded.
- Request shall move to Information Required.
- The appropriate user shall be notified.
- The responsible user shall be able to provide the required information.
- Previous workflow history shall remain available.
- The request shall return to the correct workflow stage after clarification.

Multiple clarification cycles shall be supported unless restricted by business rules.

### 18. Administrative Reassignment
Super Admin administrative intervention/reassignment shall follow defined rules. The
system shall define:
- Which roles/tasks can be reassigned.
- Who can perform reassignment.
- Whether reassignment requires a reason.
- Whether the previous assignee retains visibility.
- Whether reassignment triggers notification.
- Whether reassignment triggers re-approval.
- Whether reassignment is audited.

Administrative intervention shall not bypass mandatory approval or security controls
unless explicitly authorised by business rules.

### 19. Notifications
Mandatory notification events shall be defined using:
`Event → Recipient → Channel → Message → Mandatory/Optional`

At minimum, notifications shall cover: user account creation, credential reset,
transfer submission, approval required, clarification requested, approval, rejection,
HR action required, Payroll task assignment, IT task assignment, task blocked,
transfer completed.

Notification failure shall not corrupt or stop the core transaction unless explicitly
defined.

### 20. Audit Logging
All material business and security actions shall be recorded. Audit records shall
include, where applicable: user/actor, role, action, entity/request, date/time,
previous value, new value, status, remarks/reason.

Audit records shall be append-only and shall not be editable through normal
application functionality.

The BRD shall define:
- Who can view audit logs.
- Whether audit logs can be exported.
- Retention period.
- Whether deletion is permitted.

Plaintext passwords must never be captured in audit records.

### 21. Performance & Availability
Infrastructure-specific targets can be finalized during deployment planning, but the
application shall have minimum development/test expectations. The BRD shall define:
expected concurrent users, expected transaction volume, API response-time target, page
response-time target, API timeout, integration timeout, maximum upload size, retry
behaviour, database transaction expectations.

Performance requirements shall be validated before production deployment.

The current BRD defers these items to infrastructure planning (NFR-009), so the minimum
application-level targets should be added separately rather than leaving them
completely undefined.

### 22. Mandatory Negative Acceptance Scenarios
The following scenarios shall be included in QA/UAT:

**Security**
- User cannot access another organisation's data.
- Employee cannot access another employee's transfer.
- IT cannot access unauthorized employee documents.
- User cannot bypass first-login password change.
- Locked user cannot log in.
- Deactivated user cannot log in.
- Old password cannot be used after reset.
- Direct API access cannot bypass role/scope restrictions.

**Workflow**
- User cannot approve a request outside their scope.
- Invalid workflow transition is rejected.
- Completed request cannot be modified through normal workflow.
- IT cannot provide Final Approval while mandatory Payroll activity is incomplete.
- Request cannot become Completed without IT Final Approval.
- Required Receiving Manager approval cannot be bypassed.
- HR metadata changes trigger re-approval where required.

**Vacancy**
- Full vacancy cannot receive a new allocation.
- Concurrent HR approvals cannot over-allocate capacity.
- Vacancy capacity cannot become negative.
- Withdrawn/rejected requests release reservation according to defined rules.

**Integration**
- Integration timeout does not create duplicate transactions.
- Failed integration can be retried.
- Failed integration does not incorrectly mark the task as completed.
- External system failure does not incorrectly mark the transfer as Completed.
